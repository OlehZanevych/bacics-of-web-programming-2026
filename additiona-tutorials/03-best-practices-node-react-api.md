# Частина A. Сервер на Node.js

## 1. Структура й шари

✅ **Розділяйте код за відповідальністю:** `routes → controllers → services →
repositories`, плюс `mappers`, `validators`, `middlewares`, `errors`,
`config`. Кожен шар знає лише про сусідній.

| Шар | Робить | Ніколи не робить |
|---|---|---|
| route | метод + шлях + ланцюжок middleware | SQL, бізнес-правила |
| controller | `req` → виклик сервісу → `res` (статус, заголовки) | SQL, бізнес-правила |
| service | бізнес-правила, кидає доменні помилки | `req`, `res`, статуси, SQL |
| repository | SQL, лише параметризований | HTTP, бізнес-правила |
| mapper | рядок таблиці ↔ JSON API | усе інше |

*Чому:* заміна сховища чи формату відповіді змінює **один** шар; помилку
шукають в одному місці; сервіси можна тестувати без HTTP.
📍 `assignment-4/src/`

✅ **`app.js` налаштовує, `server.js` запускає.** `app.listen()` — лише в
точці входу. Тоді тести імпортують `app` і надсилають запити без порту.
📍 `src/app.js`, `src/server.js`, `tests/api.test.js`

✅ **Тонкі контролери.** Якщо в контролері з'явився `if` із бізнес-правилом
чи SQL — йому місце в сервісі чи репозиторії.

❌ **Один файл `index.js` на 500 рядків** з маршрутами, SQL і перевірками
разом.

## 2. Конфігурація й секрети

✅ **Усе, що відрізняється між середовищами, — змінні середовища:** адреса
бази, секрети, порт, дозволені джерела CORS, рівень логування.

✅ **Читайте їх в одному модулі** (`src/config/index.js`), а не через
`process.env` по всьому коду. Там же — перетворення типів (`Number(…)`,
розбиття списку через кому) і значення за замовчуванням.

✅ **Fail fast:** немає обов'язкової змінної або вона неприпустима (секрет
коротший за 32 символи) — процес зупиняється на старті зі зрозумілим
повідомленням. Сервер, що «якось запустився», падає пізніше й незрозуміліше.
📍 `src/config/index.js`

🔒 **`.env` — ніколи в git;** `.env.example` (без секретів, з коментарями) —
завжди. Секрет, що потрапив у публічний репозиторій, вважається
скомпрометованим **назавжди**, навіть якщо коміт видалили: міняйте його.

🔒 **Різні секрети для розробки й продакшену.** Секрет із `.env` ноутбука не
має працювати на сервері.

✅ **`PORT` — зі змінної середовища.** Хостинг сам повідомляє, на якому порту
слухати.

## 3. Обробка помилок

✅ **Власні класи помилок** (`ValidationError` 400, `UnauthorizedError` 401,
`ForbiddenError` 403, `NotFoundError` 404, `ConflictError` 409). Сервіс кидає
`throw new NotFoundError('Альбом')`, не знаючи про HTTP.
📍 `src/errors/index.js`

✅ **Один централізований обробник** (`(err, req, res, next)`, останнім
`app.use`) перетворює **будь-яку** помилку на відповідь **єдиного формату**:

```json
{ "status": 400, "message": "Помилка валідації",
  "errors": [{ "field": "title", "message": "Назва обов'язкова" }],
  "path": "/api/v1/albums", "timestamp": "2026-11-11T10:00:00.000Z" }
```

📍 `src/middlewares/errorHandler.js`

🔒 **Жодного `stack` у відповіді.** Стек розкриває структуру коду й версії
бібліотек. Неочікувана помилка → `500` із загальним повідомленням, а повний
стек — **у лог** разом з id запиту.

✅ **Відрізняйте очікувані помилки від багів.** Очікувані (4xx) — точний
статус і зрозуміле повідомлення. Баги (5xx) — загальне повідомлення клієнту,
детальний лог розробнику.

✅ **Express 5 сам передає помилки async-обробників** в обробник помилок.
Не потрібні ні `try/catch` у кожному контролері, ні обгортки
`asyncHandler` (вони були потрібні в Express 4).

✅ **Перетворюйте коди помилок бази в одному місці:** `23505` (унікальність) →
409, `23503` (зовнішній ключ) → 409, `23514` (`CHECK`) → 400, `22P02` (формат)
→ 400. 📍 `src/db/pgErrors.js`

✅ **Коректне завершення:** на `SIGTERM`/`SIGINT` — `server.close()`,
дочекатися поточних запитів, закрити пул з'єднань, вийти; плюс запасний
таймер. 📍 `src/server.js`

✅ **Не ковтайте помилки мовчки.** Порожній `catch {}` без коментаря — майже
завжди баг. Пул з'єднань має обробник `pool.on('error', …)`, інакше
обірване неактивне з'єднання «покладе» процес.

## 4. Валідація вхідних даних

🔒 **Валідуйте все, що приходить ззовні:** `req.body`, `req.query`,
`req.params`, заголовки, які використовуєте. Клієнтська валідація — для
зручності, серверна — обов'язкова.

✅ **Схеми замість ручних `if`.** Схема (Zod) одночасно **перевіряє,
очищає й перетворює**: `trim`, значення за замовчуванням, рядок → число.
Далі код працює лише з результатом (`req.validatedBody`).
📍 `src/validators/`, `src/middlewares/validate.js`

🔒 **Невідомі поля — помилка** (`.strict()`). Захист від *mass assignment*:
клієнт не протягне `"role": "ADMIN"`, `"id"` чи `"createdAt"`.

✅ **Query-параметри — завжди рядки.** Перетворюйте явно; порожній рядок —
«не задано», а не `0`.

✅ **Обмежуйте все:** довжину рядків, діапазон чисел, `limit` пагінації
(наприклад, 1–100), розмір тіла (`express.json({ limit: '100kb' })`).
Необмежений `limit=1000000` — найпростіша DoS-атака.

✅ **Повертайте всі помилки одразу** у форматі `[{ field, message }]`, щоб
клієнт показав їх біля полів, а не по одній за спробу.

✅ **Окрема схема для `PATCH`** — без значень за замовчуванням, інакше
часткове оновлення непомітно затре інші поля.

## 5. Робота з базою даних

🔒 **Лише параметризовані запити** (`$1, $2, …`). Ніколи не склеюйте SQL із
даними користувача — ні шаблонними рядками, ні конкатенацією.

```js
// ❌ pool.query(`SELECT * FROM albums WHERE title ILIKE '%${search}%'`)
// ✅
pool.query('SELECT * FROM albums WHERE title ILIKE $1', [`%${search}%`]);
```

🔒 **Ідентифікатори (стовпці сортування, напрямок) — лише з білого списку.**
Параметром їх передати неможливо. 📍 `SORT_COLUMNS` у
`src/repositories/albums.repository.js`

✅ **Один пул з'єднань на застосунок** (`pg.Pool`), модуль-одинак. Для
транзакції — `pool.connect()`, `BEGIN`/`COMMIT`/`ROLLBACK` і **обов'язково**
`client.release()` у `finally`. 📍 `src/db/pool.js`

✅ **Схема — лише міграціями**, у репозиторії, у порядку виконання.
Застосовану міграцію не редагують — пишуть нову. Кожна міграція має `down`.

✅ **Обмеження в базі — остання лінія оборони:** `NOT NULL`, `CHECK`,
`UNIQUE` (для назв — на `lower(…)`), зовнішні ключі з явним `ON DELETE`.
Перевірки в коді можуть мати баги чи гонки; обмеження бази — ні.

✅ **Індекси:** на кожен зовнішній ключ (PostgreSQL сам їх не створює), на
поля фільтрів і сортування, триграмний GIN (`pg_trgm`) для пошуку
`ILIKE '%…%'`. Перевіряйте план запиту: `EXPLAIN`.

✅ **Фільтрація, сортування, пагінація — у SQL**, не в JavaScript після
`SELECT *`. Загальна кількість — окремим `COUNT(*)` з **тими самими**
умовами (одна функція побудови `WHERE`).

✅ **Стабільний порядок для пагінації:** `ORDER BY <поле>, id`. Без
унікального другого ключа записи з однаковим значенням «перескакують» між
сторінками.

✅ **Уникайте N+1:** пов'язані дані — `JOIN` в одному запиті, а не запит на
кожен рядок.

✅ **Пам'ятайте про типи драйвера:** `COUNT(*)` (`bigint`) приходить рядком —
`::int`; `DATE` за замовчуванням стає `Date` з часовим поясом — повертайте
рядком (`types.setTypeParser(1082, v => v)`).

✅ **Незалежні запити — паралельно:** `Promise.all([findAll(), count()])`.

## 6. Дизайн REST API

✅ **Ресурси — іменники в множині**, дії — методами HTTP:
`GET /albums`, `POST /albums`, `PATCH /albums/:id`. ❌ `/getAlbums`,
`/albums/delete/:id`.

✅ **Версія в шляху:** `/api/v1/…` — щоб змінити контракт, не зламавши
старих клієнтів.

✅ **Правильні коди:**

| Ситуація | Код |
|---|---|
| успішне читання | 200 |
| створено | **201 + `Location`** + створений ресурс |
| оновлено / видалено, тіло не потрібне | **204** |
| некоректні дані (тіло, query, параметр шляху) | 400 |
| немає токена / недійсний / прострочений | 401 |
| токен дійсний, прав недостатньо | 403 |
| ресурсу за адресою немає | 404 |
| конфлікт (дублікат, порушення зв'язку) | 409 |
| забагато запитів | 429 (+ `Retry-After`) |
| збій сервера | 500 (без подробиць) |
| залежність недоступна (база) | 503 |

✅ **`PUT` — повна заміна, `PATCH` — часткова.** Обидва ідемпотентні в
нашій реалізації: повтор того самого запиту дає той самий стан (крім
службового `updated_at`). `POST` — ні.

✅ **Список із метаданими:** `{ data, total, limit, offset }` — клієнт одним
запитом отримує і сторінку, і все для пагінації.

✅ **Узгоджений формат:** camelCase у JSON, дати — ISO 8601
(`2026-11-11`, `2026-11-11T10:00:00.000Z`), `null` для відсутнього значення
(а не `""` чи `0`), однаковий формат помилок для всіх маршрутів.

✅ **Відповідь — через мапер**, а не «сирий» рядок таблиці: контракт API не
залежить від назв стовпців, і службові поля (`password_hash`) не витікають.
📍 `src/mappers/`

## 7. Безпека

🔒 **Паролі — лише хеш повільною функцією** (bcrypt з вартістю ≥ 12 або
argon2id). Ніколи — у відкритому вигляді, ніколи — SHA-256/MD5. Пам'ятайте
про обмеження bcrypt у 72 байти.

🔒 **JWT:**

- секрет щонайменше 32 символи (краще — 64 випадкові байти), лише зі змінної середовища;
- короткий строк дії (`exp`, у прикладі — 1 година);
- при перевірці — явний список алгоритмів (`algorithms: ['HS256']`);
- у payload — лише ідентифікатор і роль: **токен не шифрується**, його
  читає будь-хто;
- роль у токен кладе сервер з бази, а не з запиту.

🔒 **Перевірка прав — на сервері, на кожному маршруті.** `authenticate` →
`requireRole('ADMIN')` → валідація → контролер. Сховати кнопку в клієнті —
не захист.

🔒 **Роль ніколи не приймається від клієнта** (реєстрація завжди створює
`USER`).

🔒 **Однакова відповідь** для «немає такої пошти» і «неправильний пароль»
(і однаковий час відповіді) — щоб не розкривати, хто зареєстрований.

🔒 **Обмеження частоти** на вхід і реєстрацію (`express-rate-limit`), за
проксі — `app.set('trust proxy', 1)`, інакше всі клієнти матимуть IP
проксі.

🔒 **`helmet()`** — захисні заголовки; **CORS** — явний список джерел, не
`*` (особливо з токенами).

🔒 **Нічого чутливого в логах:** паролі, токени, заголовок `Authorization`,
cookie — через `redact` логера. 📍 `src/utils/logger.js`

🔒 **Залежності:** `npm audit`, оновлення патч-версій, `package-lock.json`
у репозиторії, `npm ci` на сервері.

✅ Звіряйтеся з **OWASP Top 10**: для навчального API найважливіші Broken
Access Control, Injection, Cryptographic Failures, Security
Misconfiguration.

## 8. Логування й моніторинг

✅ **Структурований логер** (pino) замість `console.log`: рівні
(`debug` → `fatal`), JSON у продакшені, читабельний вивід у розробці.

✅ **Один рядок на запит:** метод, шлях, статус, тривалість; рівень — за
статусом (`warn` для 4xx, `error` для 5xx).

✅ **Наскрізний id запиту** (`X-Request-Id`) — у кожному рядку логу й у
відповіді. Користувач надсилає id зі скріншота — ви знаходите запит за
секунди. 📍 `src/middlewares/requestId.js`, `httpLogger.js`

✅ **Health checks:** `/health/live` — «процес живий» (без бази),
`/health` — «готовий обслуговувати» (з перевіркою бази, 503 при збої).
Хостинг перезапускає сервіс, що не відповідає.

## 9. Тести й документація

✅ **Інтеграційні тести API** — найкраще співвідношення користі й зусиль:
`node:test` + `supertest` проти `app`, **окрема тестова база**, дані
відновлюються перед кожним тестом. Тестуйте не лише успіх, а й 400, 401,
403, 404, 409. 📍 `tests/api.test.js`

✅ **Запобіжник:** тести, що очищають таблиці, відмовляються працювати не на
тестовій базі. 📍 `tests/helpers.js`

✅ **Детермінований seed:** однакові дані при кожному запуску (генератор
псевдовипадкових чисел із фіксованим початковим значенням).

✅ **OpenAPI-опис** + Swagger UI на `/api-docs`; оновлюється разом із кодом.

✅ **README:** опис, ER-діаграма, таблиця ендпоїнтів, запуск «з нуля» на
чистому комп'ютері, тестові облікові записи, використання ШІ. Перевіряйте
інструкцію запуску на свіжому клоні репозиторію.

✅ **Файл запитів** (`requests.http`) з позитивними й негативними
сценаріями — жива документація, яку можна виконати.

## 10. Інструменти, залежності, продакшен

✅ **ES-модулі** (`"type": "module"`), імпорти з розширенням `.js`.

✅ **ESLint + Prettier**, перевірка перед комітом: `npm run lint`,
`npm run format:check`, `npm test`.

✅ **`node --watch`** для розробки — `nodemon` не потрібен.

✅ **Версія Node.js зафіксована:** `"engines"` у `package.json` і `.nvmrc`.

✅ **`dependencies` vs `devDependencies`:** лінтери, тести, `pino-pretty` —
у `devDependencies`; на хостингу з `NODE_ENV=production` вони не
встановлюються.

✅ **Продакшен:** `NODE_ENV=production`, `npm start` (не `dev`), міграції
перед запуском (`npm run migrate:up && npm start`), секрети — у налаштуваннях
хостингу, health check налаштований.

# Частина B. Виклик REST API в React

## 11. Шар API

✅ **Жодного `fetch` у компонентах.** Один модуль (`api/http.js`) знає
базову адресу, додає заголовки й токен, розбирає JSON і помилки. Над ним —
модулі ресурсів (`albumsApi.list`, `albumsApi.create`…). Компоненти
отримують **або дані, або помилку**. 📍 `assignment-5/client/src/api/`

✅ **Базова адреса — зі змінної середовища** (`import.meta.env.VITE_API_URL`),
різна для розробки й продакшену.

✅ **Пам'ятайте особливості `fetch`:**

- ⚠️ **не кидає помилку на 4xx/5xx** — перевіряйте `response.ok`;
- відхиляє проміс з `TypeError` при мережевій невдачі (сервер недоступний, CORS), а при скасуванні — з `AbortError` (`DOMException`);
- `204 No Content` не має тіла — не викликайте `response.json()`;
- тіло розбирайте як JSON, лише якщо `Content-Type` — JSON.

✅ **Власний клас помилки** (`HttpError` зі `status`, `body`, гетерами
`isValidation`, `isConflict`, `fieldErrors`) — сторінки перевіряють
`error.isConflict`, а не магічні числа.

✅ **Перетворення «мова інтерфейсу ↔ мова API» — у шарі API:** сторінка
говорить `page`/`size`, сервер — `limit`/`offset`; порожні фільтри в запит не
потрапляють.

## 12. Завантаження даних і чотири стани

✅ **Кожен запит має чотири стани** — і кожен потребує інтерфейсу:

| Стан | Інтерфейс |
|---|---|
| завантаження (уперше) | скелетон (структура сторінки) або спінер для одного запису |
| завантаження (оновлення) | старі дані приглушено + `aria-busy="true"` |
| помилка | зрозуміле повідомлення + «Спробувати ще раз» |
| порожньо | окремі тексти для «нічого немає», «нічого не знайдено» (+ «Скинути фільтри»), «такої сторінки немає» |
| дані | вміст |

✅ **Статус — одне значення** (`'loading' | 'success' | 'error'`), а не
три незалежні булеві `isLoading`, `isError`, `isSuccess`, які можуть
суперечити одне одному.

✅ **Не зберігайте похідне в стані.** Якщо значення можна обчислити з
наявних даних під час рендеру — обчислюйте. У прикладі статус обчислюється
з ключа запиту, для якого отримано відповідь. 📍 `hooks/useAsync.js`

✅ **Розрізняйте «не знайдено» й «збій»:** 404 (і 400 для неправильного id
в адресі) — сторінка «немає такого запису»; мережа/500 — помилка з повтором.

✅ **Незалежні запити — паралельно**, а не «водоспадом» (другий чекає
першого без потреби).

## 13. Ефекти, гонки й скасування

✅ **Скасовуйте застарілі запити:** `AbortController` у функції очищення
ефекту. Без цього швидке перемикання сторінок показує дані попередньої
(відповіді приходять не в порядку запитів).

```js
useEffect(() => {
  const controller = new AbortController();
  api.get(id, { signal: controller.signal }).then(setData, handleError);
  return () => controller.abort();
}, [id]);
```

✅ **Ігноруйте `AbortError`** — це не помилка для користувача.

✅ **`StrictMode` у розробці монтує компоненти двічі** — у Network видно
скасований перший запит. Це перевірка, що очищення працює, а не баг.

✅ **Залежності ефекту — примітиви.** Об'єкт чи функція, створені під час
рендеру, нові щоразу → нескінченні запити. Використовуйте ключ-рядок
(`JSON.stringify(query)`) і `useRef` для найсвіжішої функції.

✅ **Слухайте лінтер хуків** (`eslint-plugin-react-hooks` 7): правило
`set-state-in-effect` майже завжди означає, що стан можна обчислити, а
`exhaustive-deps` — що ефект бачить застарілі значення.

## 14. Списки: стан в адресі, debounce, пагінація на сервері

✅ **Пошук, фільтри, сортування, сторінка — у query-параметрах адреси**
(`useSearchParams`). Посиланням можна поділитися, F5 і «Назад» працюють.
📍 `utils/listQuery.js`, `hooks/useListQuery.js`

✅ **Перевіряйте параметри з адреси** (`?page=abc`) і підставляйте значення
за замовчуванням; не пишіть в адресу значень за замовчуванням.

✅ **Зміна фільтра скидає сторінку на 1.**

✅ **Debounce для пошуку** (≈ 300 мс): запит — коли користувач перестав
друкувати. Поле при цьому оновлюється миттєво. Очищення пошуку — без
затримки.

✅ **`replace: true` для введення в пошук** — не засмічуйте історію
браузера кожною літерою.

✅ **Фільтрація, сортування й пагінація — на сервері.** Клієнт ніколи не
завантажує «всі записи», щоб відфільтрувати їх сам.

✅ **Структурно різні макети** — через CSS, коли змінюється лише
розташування; через `useMediaQuery` (на `useSyncExternalStore`), коли
змінюється розмітка (таблиця ↔ картки).

## 15. Зміна даних і форми

✅ **Блокуйте повторне надсилання:** `disabled` на кнопці під час запиту й
перевірка `isSubmitting` в обробнику — подвійний клік не створить два
записи.

✅ **Після зміни — оновіть дані** (перезавантажте список, `reload()`) або
перейдіть на сторінку результату. Після видалення — `navigate(…, {
replace: true })`, щоб «Назад» не вів на видалений запис.

✅ **Зворотний зв'язок:** сповіщення про успіх і невдачу (`aria-live`).

✅ **Дві валідації:** клієнтська — миттєва, для зручності; серверна —
обов'язкова. **Помилки сервера показуйте біля полів**: `[{ field, message }]`
→ `{ field: message }`. 409 (дублікат) — біля поля, якого він стосується.
📍 `hooks/useAlbumForm.js`, `HttpError.fieldErrors`

✅ **Фокус на перше помилкове поле** після невдалого надсилання;
`aria-invalid` і `aria-describedby` зв'язують поле з помилкою.

✅ **Перетворення типів — в одному модулі:** поля форми — рядки, API чекає
числа, `null`, булеві. 📍 `features/albums/albumFormValues.js`

✅ **Одна форма для створення й редагування;** `key` на формі, щоб при
зміні запису вона створювалася заново з новими початковими значеннями.

❌ **Не кидайте помилку з обробника далі «в нікуди»** — у консолі з'явиться
`Uncaught (in promise)`. Кожна помилка має бути показана в одному місці.

## 16. Автентифікація в клієнті

✅ **Стан автентифікації — у Context** (користувач, `isAuthenticated`,
`isAdmin`, `signIn`, `signOut`); значення — через `useMemo`.
📍 `context/AuthProvider.jsx`

✅ **Токен додається до запитів в одному місці** — у `http.js`.

✅ **401 обробляється глобально:** видалити токен → «вийти» → сторінка входу
з поверненням туди, де користувач був. Модуль API повідомляє React-дерево
подією, а не імпортом навігації.

✅ **Перевіряйте `exp` при завантаженні** — прострочений токен = не увійшов.

⚠️ **`localStorage` для токена — компроміс:** просто, переживає
перезавантаження, але доступний будь-якому скрипту на сторінці (XSS).
Безпечніше: access-токен у пам'яті + refresh-токен у `httpOnly`-cookie. У
будь-якому разі — жодного `dangerouslySetInnerHTML` з даних користувача.

🔒 **`ProtectedRoute` і приховані кнопки — зручність, не захист.** Кожну дію
сервер перевіряє сам; клієнт лише **відображає** права, отримані від
сервера.

## 17. Помилки, доступність, безпека клієнта

✅ **Повідомлення — для людей:** «Не вдалося з'єднатися з сервером»,
«Сервер тимчасово недоступний», а для 4xx — повідомлення сервера. Ніяких
`TypeError: Failed to fetch` і JSON на екрані.

✅ **Консоль чиста:** жодних `Uncaught`, попереджень React (ключі, керовані
поля), помилок CORS. (Рядки «Failed to load resource: 404» для очікуваних
відповідей — журнал мережі браузера, не помилка коду.)

✅ **Доступність асинхронного інтерфейсу:** `aria-busy` на області, що
оновлюється; `aria-live` для лічильників і сповіщень; `role="alert"` для
помилок; керування фокусом у модальних вікнах (нативний `<dialog>` зі
`showModal()`).

🔒 **У клієнті немає секретів.** Усе з `VITE_*` вбудовується в зібраний
JavaScript. Адреса API — так, ключі сторонніх сервісів із правом запису —
ніколи (такі запити йдуть через ваш сервер).

✅ **Розумійте CORS:** це браузерний захист **користувача**; сервер
дозволяє конкретні джерела. Помилка CORS у консолі — привід перевірити
`CORS_ORIGINS` на сервері й порт клієнта, а не вимикати перевірку.

## 18. Коли брати бібліотеку

Власний `useAsync` у прикладі написано, щоб **зрозуміти механіку**: стани,
скасування, гонки. У робочих проєктах для серверних даних зазвичай беруть
бібліотеку, яка додає кешування, дедуплікацію однакових запитів,
повторні спроби, оновлення у фоні й інвалідацію після мутацій:

| Інструмент | Коли |
|---|---|
| **TanStack Query** | найпоширеніший вибір для клієнтських SPA |
| **SWR** | легша альтернатива для простих сценаріїв читання |
| **React Router** (`loader` / `action`) | коли дані прив'язані до маршрутів (data mode з `createBrowserRouter` або framework mode, зокрема з рендерингом на сервері) |

Правила з цієї шпаргалки — чотири стани, скасування, помилки біля полів,
стан в адресі — лишаються тими самими й з бібліотекою: вона лише бере на
себе частину рутини.
